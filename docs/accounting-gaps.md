# จุดบอดทางบัญชีของระบบสต็อกปัจจุบัน

ตรวจจากโค้ดจริง (`schema-stock.sql`, `pos-sell.html`) — ไม่ใช่การคาดเดา

---

## สรุปสั้น

ระบบสต็อกที่มีอยู่ **ใช้คุมของได้ดี แต่ยังใช้ทำบัญชีไม่ได้**

ต่างกันตรงนี้:
- **คุมของ** = ตอบว่า *ของเหลือเท่าไร ใครเบิกไป หายไปกี่หน่วย* → ระบบทำได้ครบ ✅
- **ทำบัญชี** = ตอบว่า *เดือนนี้ต้นทุนขายเท่าไร กำไรจริงเท่าไร สต็อกต้นเดือน-สิ้นเดือนมูลค่าเท่าไร* → **ยังตอบไม่ได้** ❌

---

## จุดบอด 8 ข้อ เรียงตามความรุนแรง

### 🔴 1. ใช้ต้นทุนล่าสุดทับของเก่าทั้งหมด

**โค้ดจริง** (`schema-stock.sql:178`)
```sql
update public.ingredients set cost = (v_line->>'unit_cost')::numeric where id = v_ing;
```

รับของเข้าครั้งใหม่ = **ต้นทุนของทั้งคลังเปลี่ยนทันที** ทั้งที่ของเก่ายังอยู่

**ตัวอย่างที่ทำให้ตัวเลขเพี้ยน**
```
1 ก.ย.  มีนม 10,000 ml ทุน 0.040/ml  → มูลค่าสต็อก 400 บาท
5 ก.ย.  ซื้อเพิ่ม 2,000 ml ทุน 0.060  → ระบบตั้งทุน = 0.060 ทุกหน่วย
        มูลค่าสต็อกกลายเป็น 12,000 × 0.060 = 720 บาท
        ทั้งที่จ่ายเงินซื้อจริงแค่ 400 + 120 = 520 บาท
        ➜ "กำไร" โผล่มา 200 บาท จากอากาศ
```

มาตรฐานบัญชีต้องใช้ **ถัวเฉลี่ยถ่วงน้ำหนัก** หรือ **FIFO**
วิธีถัวเฉลี่ย: `(400+120) ÷ 12,000 = 0.0433/ml` → มูลค่า 520 บาท ตรงกับเงินที่จ่ายจริง

**ผลกระทบ:** ต้นทุนขายและกำไรในรายงานผิดทุกครั้งที่ราคาซื้อเปลี่ยน

---

### 🔴 2. การขายไม่บันทึกต้นทุน ณ เวลานั้น

**โค้ดจริง** (`pos-sell.html:1100`) — ตอนขายส่งแค่ `ingredient_id` กับ `qty` ไม่ส่ง `unit_cost`

```js
p_lines: lines   // [{ingredient_id, qty}] — ไม่มี unit_cost
```

ผลคือ `stock_moves.unit_cost` ของรายการขายเป็น **null ทุกแถว**

**ผลกระทบ:** ย้อนกลับไปคำนวณต้นทุนขายของเดือนที่แล้วไม่ได้เลย ต้องเดาจากต้นทุนปัจจุบัน ซึ่งเปลี่ยนไปแล้ว

---

### 🔴 3. ไม่มีมูลค่าสต็อกย้อนหลัง

`stock_overview` คำนวณ **ยอดปัจจุบัน** เท่านั้น ไม่มีการเก็บภาพนิ่งรายเดือน

สูตรบัญชีพื้นฐานที่ใช้ไม่ได้:
```
ต้นทุนขาย = สต็อกต้นงวด + ซื้อระหว่างงวด − สต็อกปลายงวด
```
เพราะไม่รู้ว่า "สต็อกต้นงวด" เมื่อ 1 ก.ย. มูลค่าเท่าไร

---

### 🟠 4. ของขายต่อ (ขนม/น้ำอัดลม) ไม่มีต้นทุน

กล้วยตาก · ทองม้วน · น้ำอัดลม · ทิชชู่ — ขายเป็นเมนู แต่**ไม่ได้อยู่ในตารางวัตถุดิบ**

ผลคือ `menuCost()` คืนค่า **0** → ระบบคิดว่ากำไร 100%

จากใบกระดาษ: น้ำอัดลมขาย 16 บาท ถ้าทุน 12 บาท กำไรจริง 4 บาท แต่ระบบรายงาน 16 บาท

---

### 🟠 5. รายจ่ายประจำวันไม่มีที่บันทึก

ใบกระดาษมีครบ แต่ระบบไม่มี:

| รายการ | ในกระดาษ | ในระบบ |
|---|---|---|
| น้ำแข็ง 4 ถุง | 140 | ❌ |
| หนังสือพิมพ์ | 30 | ❌ |
| น้ำมะนาว | 25 | ❌ |
| ของแจกฟรี | 30 | ❌ |
| ค่าเช่า / ค่าแรง / ค่าน้ำไฟ | — | ❌ |

**"กำไรขั้นต้น" ในระบบ = ยอดขาย − ต้นทุนวัตถุดิบเท่านั้น** ยังไม่ใช่กำไรจริง

> หมายเหตุ: เงินที่หยิบออกจากลิ้นชักไปซื้อของ บันทึกได้ใน `cash_movements` แล้ว
> แต่นับเป็น "เงินออกจากลิ้นชัก" ไม่ได้ลงเป็น "ค่าใช้จ่าย" ในงบกำไรขาดทุน

---

### 🟠 6. ของที่จ่ายออกไปสาขาอื่น ไม่มีการจัดประเภท

`issue` ตัดของออกจากคลัง บันทึกว่าใครรับ — แต่ทางบัญชีมันคืออะไร?

- **ขายให้สาขาพ่อ** → ต้องเป็นรายได้ + ลูกหนี้
- **ให้ยืม** → ลูกหนี้อย่างเดียว
- **เจ้าของเอาไปใช้เอง** → เงินถอนทุน (drawings)

ตอนนี้ระบบแค่ทำให้ของหายจากคลัง โดยไม่บอกว่าเป็นรายจ่ายหรือรายได้ → **ต้นทุนหายไปจากงบ ไม่มีรายรับมารับ**

---

### 🟡 7. แก้ย้อนหลังได้ไม่จำกัด

`set_stock_count` เขียนทับยอดได้ทุกเมื่อ ไม่มีการ **ปิดงวด**

หมายความว่ารายงานเดือน ส.ค. ที่พิมพ์ไปแล้ว อาจเปลี่ยนตัวเลขได้ถ้ามีคนปรับสต็อกย้อนหลัง — บัญชีที่ตรวจสอบได้ต้องล็อกงวดที่ปิดแล้ว

*(ข้อดี: มีประวัติใน `stock_moves` ทุกครั้ง ตรวจสอบได้ว่าใครแก้ — แค่ห้ามแก้ไม่ได้)*

---

### 🟡 8. ไม่มีเจ้าหนี้ / ใบกำกับ / VAT

`stock_docs` มีช่อง `supplier` เป็นข้อความ แต่ไม่มี:
- เลขที่ใบกำกับ
- จ่ายแล้ว/ค้างจ่าย
- แยก VAT

ตอนนี้ยังไม่จด VAT จึงไม่กระทบ **แต่ถ้าวันหนึ่งจด จะต้องรื้อ**

---

## ✅ สิ่งที่ระบบทำได้ดีแล้ว

| | |
|---|---|
| ประวัติการเคลื่อนไหวครบ | `stock_moves` เก็บทุกครั้ง ลบไม่ได้ ตรวจย้อนหลังได้ |
| แยกสถานที่ | คลัง / หน้าร้าน แยกกันชัด |
| ตัดสต็อกแบบ atomic | สองเครื่องขายพร้อมกันไม่เพี้ยน |
| ตรวจนับจริง | บันทึกส่วนต่างเป็นเอกสาร มีคนทำ มีเวลา |
| กระทบยอดเงินสด | กะ + เงินเข้า-ออกลิ้นชัก ตรงตามหลักการ |

**โครงสร้างพื้นฐานถูกต้องแล้ว** — สิ่งที่ขาดคือชั้นบัญชีที่วางทับ ไม่ต้องรื้อของเดิม

---

## แผนแก้ แบ่งเป็น 3 ระดับ

### ระดับ 1 — แก้ให้ตัวเลขต้นทุนถูก (จำเป็น · 2–3 วัน)

1. **เปลี่ยนเป็นถัวเฉลี่ยถ่วงน้ำหนัก**
   ```sql
   -- ตอนรับของ: ต้นทุนใหม่ = (มูลค่าเดิม + มูลค่าที่ซื้อ) ÷ (จำนวนเดิม + จำนวนที่ซื้อ)
   new_cost = (old_qty*old_cost + in_qty*in_cost) / (old_qty + in_qty)
   ```
2. **บันทึก `unit_cost` ตอนขาย** — ส่งต้นทุน ณ เวลานั้นไปกับ `stock_moves` ด้วย
3. **ใส่ต้นทุนให้ของขายต่อ** — เพิ่มขนม/น้ำอัดลมเป็นวัตถุดิบ ผูกสูตร 1:1

> ทำแค่ 3 ข้อนี้ ตัวเลขกำไรในรายงานจะเชื่อถือได้

### ระดับ 2 — ทำให้เป็นบัญชีจริง (2 สัปดาห์)

4. **ตารางค่าใช้จ่าย** (`expenses`) — น้ำแข็ง ค่าเช่า ค่าแรง ค่าน้ำไฟ แยกหมวด
5. **ปิดงวดรายเดือน** — เก็บภาพนิ่งมูลค่าสต็อก ล็อกไม่ให้แก้ย้อนหลัง
6. **จัดประเภทของที่จ่ายออกสาขา** — ขาย / ให้ยืม / ถอนทุน
7. **งบกำไรขาดทุนรายเดือน** — รายได้ − ต้นทุนขาย − ค่าใช้จ่าย = กำไรสุทธิ

### ระดับ 3 — เมื่อจำเป็น

8. เจ้าหนี้การค้า + ใบกำกับ + VAT (ทำตอนจด VAT)

---

## ข้อเสนอ

**ทำระดับ 1 ก่อน** — เพราะตอนนี้ระบบแสดง "กำไรขั้นต้น" ให้เห็นทุกหน้า **แต่ตัวเลขนั้นยังไม่จริง**
ปล่อยไว้อันตรายกว่าไม่มีเลย เพราะคุณอาจตัดสินใจจากตัวเลขที่ผิด

ระดับ 2 ค่อยทำเมื่อพร้อมจะทำบัญชีเต็มรูปแบบ — และควรทำพร้อมกับเรื่องรับรายงานรายวันจากสาขาที่ยังใช้กระดาษ เพราะใช้ตารางค่าใช้จ่ายชุดเดียวกัน
