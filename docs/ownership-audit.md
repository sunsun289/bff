# วิธีตรวจข้อผิดพลาด "เชิงออกแบบ" — Banfa POS

**ปัญหา:** บั๊กแบบ "กะเก็บในเครื่อง" ตรวจด้วย grep / parse / ทดสอบกดปุ่ม **ไม่เจอ**
เพราะโค้ดถูกทุกบรรทัด สิ่งที่ผิดคือ **สมมติฐานเกี่ยวกับโลกจริง**

เอกสารนี้คือชุดคำถามที่จับบั๊กประเภทนั้นได้ + ผลตรวจปัจจุบัน

## 6 คำถามที่จับบั๊กเชิงออกแบบ

### 1. ข้อมูลชิ้นนี้ "เป็นของใคร"
ถามกับข้อมูลทุกชิ้น: เป็นของ **เครื่อง** / ของ **คน** / ของ **ร้าน**?

| เป็นของ | ต้องเก็บที่ | ตัวอย่าง |
|---|---|---|
| เครื่อง | localStorage | ธีมสี, token |
| คน | เซิร์ฟเวอร์ ผูก user | สิทธิ์, PIN |
| **ร้าน** | **เซิร์ฟเวอร์** | **กะ, บิล, สต็อก, เมนู** |

> ❌ บั๊กที่เจอ: กะเป็นของ**ร้าน** แต่เก็บใน**เครื่อง** → แต่ละเครื่องเปิดกะของตัวเอง

### 2. เปิด 2 เครื่องพร้อมกันจะเกิดอะไร
ไล่ทุกหน้าจอ: ถ้าแท็บเล็ตหน้าร้าน + มือถือที่บ้าน เปิดพร้อมกัน
- เห็นตัวเลขเดียวกันไหม
- แก้พร้อมกันแล้วของใครหาย
- ใครกดก่อน/หลัง ผลต่างกันไหม

### 3. ล้าง cache แล้วเสียอะไร
กด "ล้างข้อมูลเว็บไซต์" บนเบราว์เซอร์ → ข้อมูลไหนหายถาวร
ถ้าหายแล้ว**เสียเงินหรือเสียหลักฐาน** = ต้องย้ายขึ้นเซิร์ฟเวอร์

### 4. เน็ตล่มตรงกลางขั้นตอน
สำหรับทุกงานที่มีหลายขั้น (ขาย → ตัดสต็อก → นับเข้ากะ):
ถ้าล่มระหว่างขั้น 2 ระบบอยู่ในสภาพไหน กู้ได้ไหม

> ❌ บั๊กที่เจอ: บิลไม่เข้าระบบ แต่สต็อกถูกตัดไปแล้ว → ขายซ้ำตัดสองรอบ

### 5. เวลาผ่านไปแล้วยังทำงานไหม
- token หมดอายุ (1 ชม.) ❌ เคยพัง แก้แล้ว
- เปิดค้างข้ามวัน แล้ววันที่ยังถูกไหม
- ข้อมูลสะสมถึงเพดาน limit แล้วเงียบไหม

### 6. คนใช้จริงเข้าใจตรงกับที่โค้ดคิดไหม
- พนักงานเห็นข้อความแล้วรู้ไหมว่าต้องทำอะไรต่อ
- สิ่งที่หน้าจอบอก ตรงกับสิ่งที่เกิดขึ้นจริงไหม

## ผลตรวจปัจจุบัน (v2026.08.31-a)

### ✅ ผ่าน — เก็บถูกที่แล้ว

| ข้อมูล | เก็บที่ | ถูกต้องเพราะ |
|---|---|---|
| ธีมสี | เครื่อง | ความชอบต่อเครื่อง |
| auth token | เครื่อง | ชั่วคราว สร้างใหม่ได้ |
| เงินทอนตั้งต้นล่าสุด | เครื่อง | แค่ค่าจำเพื่อสะดวก |
| บิล / กะ / เงินลิ้นชัก | เซิร์ฟเวอร์ | เป็นของร้าน |
| สต็อก / วัตถุดิบ / เอกสารคลัง | เซิร์ฟเวอร์ | เป็นของร้าน |
| เมนู / สูตร / ตัวเลือก / ตั้งค่า | เซิร์ฟเวอร์ | เป็นของร้าน |
| PIN พนักงาน | เซิร์ฟเวอร์ (hash) | ความปลอดภัย |

### ⚠️ ยังมีความเสี่ยง — เรียงตามความรุนแรง

| # | เรื่อง | ความเสี่ยง | ทางแก้ |
|---|---|---|---|
| 1 | `failed_sales` อยู่ในเครื่องอย่างเดียว | ล้าง cache = **บิลที่รับเงินแล้วหายถาวร** ไม่มีหลักฐาน | ทำหน้า "บิลค้าง" ให้กดส่งซ้ำ + เตือนก่อนล้าง |
| 2 | `failed_stock` อยู่ในเครื่องอย่างเดียว | การตัดสต็อกที่ล้มเหลวหายไป → สต็อกเพี้ยนโดยไม่รู้ตัว | ทำปุ่มส่งซ้ำ หรืออย่างน้อยแสดงให้เห็น |
| 3 | `app_config` เขียนทับทั้งก้อน | แอดมิน 2 คนแก้เมนูพร้อมกัน **ของคนแรกหาย** | แยก `menu`/`recipes` เป็นตารางจริงเหมือน `ingredients` |
| 4 | `AUTH_PASSWORD` อยู่ใน source | ใครเปิด view-source ก็เข้าฐานข้อมูลได้ | Worker proxy เก็บ key ฝั่งเซิร์ฟเวอร์ |
| 5 | ยอดกะ refresh ทุก 2 นาที | 2 เครื่องขายพร้อมกัน ตัวเลขต่างกันได้ชั่วคราว | ยอมรับได้ หรือใช้ Supabase Realtime |
| 6 | รายงานจำกัด 3,000 บิล | เกินแล้วเตือน แต่ยังดูข้อมูลเก่าไม่ได้ | ทำ pagination หรือ DB view สรุป |

### ❓ ยังไม่เคยทดสอบจริง

- ขายพร้อมกัน 2 เครื่องในกะเดียวกัน → ยอดตรงไหม
- ปิดกะจากเครื่อง A ขณะเครื่อง B กำลังขาย
- ล้าง cache กลางกะแล้วเปิดใหม่
- เปิดค้างข้ามเที่ยงคืน → บิลลงวันไหน
- สต็อกติดลบเมื่อขายเกินที่มี

## ทดสอบเองได้ ไม่ต้องรอผม

**A. ทดสอบ 2 เครื่อง (สำคัญสุด)**
1. เปิดหน้าขายบนคอม + บนแท็บเล็ต ล็อกอินทั้งคู่
2. ทั้งคู่ต้องขึ้น **กะเดียวกัน** (เวลาเปิดกะตรงกัน)
3. ขาย 1 บิลจากคอม → รอ 2 นาที → แท็บเล็ตยอดต้องขยับตาม
4. ปิดกะจากคอม → แท็บเล็ตต้องรู้ว่ากะปิดแล้ว

**B. ทดสอบเน็ตล่ม**
1. ปิด WiFi → ขาย 1 บิล → ต้องขึ้นวงกลมแดง "บิลนี้ไม่เข้าระบบ"
2. เช็คว่าสต็อก **ไม่ถูกตัด**
3. เปิด WiFi → ขายซ้ำ → ต้องตัดสต็อกครั้งเดียว

**C. ทดสอบ token หมดอายุ**
1. เปิดหน้าขายค้างไว้ **เกิน 1 ชั่วโมง**
2. ขาย 1 บิล → ต้องผ่านปกติ ไม่มี JWT expired

**D. ทดสอบล้าง cache**
1. จดยอดกะปัจจุบันไว้
2. F12 → Application → Clear site data
3. เปิดใหม่ ล็อกอิน → **ต้องกลับเข้ากะเดิม ยอดเท่าเดิม**

ถ้าข้อไหนไม่ผ่าน บอกมา ผมแก้ให้

- **ก่อนเริ่มใช้จริงเต็มรูปแบบ**
- **เมื่อจะเพิ่มเครื่องขายเครื่องที่ 2**
- **ก่อนขยายไปสาขาอื่น** ← สำคัญมาก เพราะ "ของร้าน" จะกลายเป็น "ของสาขา" ทุกคำถามต้องตอบใหม่หมด
