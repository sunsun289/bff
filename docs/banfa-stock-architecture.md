# Banfa POS — โครงสร้างระบบคลังสินค้า & แผนปรับปรุง (ฉบับเสนอเพื่ออนุมัติ)

**สถานะ:** รอการอนุมัติ — ยังไม่เริ่มเขียนโค้ด
**ขอบเขต:** โมดูลคลัง (คลังหลังร้าน → หน้าร้าน → จ่ายสาขา) + Sprint 0/1/2 จาก Audit
**ไม่รวม:** Multi-branch POS เต็มรูปแบบ (เลื่อนไปทีหลังตามที่ตกลง)

---

## 1. ปัญหาที่โครงสร้างปัจจุบันแก้ไม่ได้

ตอนนี้ `ingredients` เก็บ **สต็อกเป็นตัวเลขเดียวต่อวัตถุดิบ**:

```json
{ "id":"i_milk", "name":"นมสด", "unit":"ml", "stock":6000, "cost":0.05 }
```

ทำให้ตอบคำถามพวกนี้ไม่ได้:
- นม 6,000 ml นี้อยู่ **ที่ไหน** — ในตู้หน้าร้าน หรือในคลังหลังร้าน?
- เดือนนี้ **จ่ายของไปสาขาบางจากเท่าไร**?
- ของหายไป 500 ml — **หายตอนไหน ใครเบิก**?
- ซื้อนมเข้ามา 10 ลัง แต่ระบบให้กรอกเป็น ml ต้องคูณเอง

และปัญหาเชิงเทคนิค: เขียนทับทั้งก้อน → 2 เครื่องขายพร้อมกันสต็อกเพี้ยน (ข้อ A1 ใน Audit)

## 2. โครงสร้างที่เสนอ

### 2.1 แนวคิดหลัก — แยก "ของ" ออกจาก "ของอยู่ที่ไหน"

```
วัตถุดิบ (ingredients)          = ข้อมูลของ: ชื่อ, หน่วย, ต้นทุน
   ↓
สถานที่ (locations)             = คลังหลังร้าน / หน้าร้าน / สาขาที่ยังไม่มี POS
   ↓
ยอดคงเหลือ (stock_levels)       = วัตถุดิบ A ที่สถานที่ B เหลือเท่าไร
   ↓
รายการเคลื่อนไหว (stock_moves)  = ประวัติทุกการเคลื่อนไหว (ledger)
```

**หลักการสำคัญ:** ยอดคงเหลือทุกตัวต้อง **อธิบายได้ด้วยประวัติ** — ถ้ายอดไม่ตรง ย้อนดูได้ว่าเกิดอะไรขึ้น

### 2.2 ผังการไหลของสต็อก

```
                    ┌──────────────────────┐
   ซื้อของเข้า ────→ │  คลังหลังร้าน         │
   (purchase_in)    │  (warehouse)         │
                    └───┬──────────────┬───┘
                        │              │
              เบิกมาหน้าร้าน      จ่ายไปสาขา
              (transfer)         (issue_out)
                        │              │
                        ▼              ▼
              ┌──────────────┐  ┌──────────────────┐
              │  หน้าร้าน     │  │ สาขาที่ยังไม่มี POS │
              │  (front)     │  │ (branch)         │
              └──────┬───────┘  └──────────────────┘
                     │                   │
              ขายตัดสต็อก          ไม่ตัดอัตโนมัติ
              (sale_out)          (บันทึกว่าจ่ายไปแล้ว)
                     │
                     ▼
              ปรับยอด/ของเสีย
              (adjust / waste)
```

### 2.3 โครงสร้างตาราง

```sql
-- สถานที่เก็บของ
create table locations (
  id         text primary key,        -- 'wh', 'front', 'br_bangchak'
  name       text not null,           -- 'คลังหลังร้าน'
  type       text not null,           -- 'warehouse' | 'front' | 'branch'
  has_pos    boolean default false,   -- สาขานี้มี POS ไหม
  active     boolean default true,
  sort_order int default 0
);

-- วัตถุดิบ (ไม่มีคอลัมน์ stock แล้ว)
create table ingredients (
  id          text primary key,
  name        text not null,
  unit        text not null,          -- หน่วยที่ใช้ในสูตร: g, ml, ใบ
  cost        numeric default 0,      -- ต้นทุนต่อหน่วยใช้งาน
  low_qty     numeric default 0,      -- จุดเตือนของหน้าร้าน
  low_qty_wh  numeric default 0,      -- จุดเตือนของคลัง
  -- หน่วยซื้อ (แก้ปัญหาซื้อเป็นลัง ใช้เป็น ml)
  buy_unit    text,                   -- 'ลัง'
  buy_factor  numeric default 1,      -- 1 ลัง = 12000 ml → 12000
  active      boolean default true
);

-- ยอดคงเหลือ แยกตามสถานที่
create table stock_levels (
  ingredient_id text references ingredients(id) on delete cascade,
  location_id   text references locations(id)   on delete cascade,
  qty           numeric not null default 0,
  updated_at    timestamptz default now(),
  primary key (ingredient_id, location_id)
);

-- ประวัติทุกการเคลื่อนไหว (ห้ามลบ ห้ามแก้)
create table stock_moves (
  id            uuid primary key default gen_random_uuid(),
  doc_id        text,                 -- เอกสารเดียวกัน = หลายบรรทัดผูกกัน
  created_at    timestamptz default now(),
  type          text not null,        -- purchase_in|transfer|issue_out|sale_out|adjust|waste
  ingredient_id text not null,
  qty           numeric not null,     -- + เข้า / − ออก
  from_location text,
  to_location   text,
  unit_cost     numeric,
  actor         text,                 -- ใครทำ
  ref           text,                 -- เลขบิลซื้อ / order local_id
  note          text
);

-- เอกสาร (หัวเอกสารของการรับ/เบิก/จ่ายหลายรายการพร้อมกัน)
create table stock_docs (
  id          text primary key,       -- 'RC-20260829-001'
  created_at  timestamptz default now(),
  type        text not null,          -- receive | transfer | issue | adjust
  from_location text,
  to_location   text,
  actor       text,
  supplier    text,                   -- สำหรับรับซื้อ
  total_cost  numeric default 0,
  note        text,
  status      text default 'posted'   -- draft | posted | cancelled
);
```

### 2.4 ทำไมต้องมี `stock_docs` แยกจาก `stock_moves`

เพราะคุณต้องการ **เพิ่มสต็อกทีละหลายรายการ** — 1 เอกสาร = หลายบรรทัด

```
เอกสาร RC-20260829-001  "รับของจาก แม็คโคร"
├─ นมสด        +12,000 ml   ต้นทุน 0.048/ml   ฿576
├─ เมล็ดกาแฟ    +5,000 g     ต้นทุน 0.62/g     ฿3,100
├─ แก้ว 16oz    +500 ใบ      ต้นทุน 2.15/ใบ    ฿1,075
└─ หลอด        +1,000 ชิ้น   ต้นทุน 0.33/ชิ้น   ฿330
                                        รวม  ฿5,081
```

กดบันทึกครั้งเดียว → สร้าง 1 doc + 4 moves + อัปเดต 4 stock_levels แบบ atomic

### 2.5 ทุกอย่างผ่าน RPC เดียว (แก้ race condition ไปในตัว)

```sql
create or replace function post_stock_doc(
  p_type text, p_from text, p_to text,
  p_actor text, p_supplier text, p_note text,
  p_lines jsonb   -- [{"ingredient_id":"i_milk","qty":12000,"unit_cost":0.048}, ...]
) returns text
language plpgsql security definer as $$
declare
  v_doc text; v_line jsonb; v_total numeric := 0;
begin
  v_doc := upper(left(p_type,2)) || '-' || to_char(now(),'YYYYMMDD') || '-'
           || lpad((select count(*)+1 from stock_docs
                    where created_at::date = current_date)::text, 3, '0');

  insert into stock_docs(id,type,from_location,to_location,actor,supplier,note)
  values (v_doc,p_type,p_from,p_to,p_actor,p_supplier,p_note);

  for v_line in select * from jsonb_array_elements(p_lines) loop
    -- ตัดออกจากต้นทาง
    if p_from is not null then
      insert into stock_levels(ingredient_id,location_id,qty)
      values (v_line->>'ingredient_id', p_from, -(v_line->>'qty')::numeric)
      on conflict (ingredient_id,location_id)
      do update set qty = stock_levels.qty - (v_line->>'qty')::numeric,
                    updated_at = now();
    end if;
    -- เพิ่มเข้าปลายทาง
    if p_to is not null then
      insert into stock_levels(ingredient_id,location_id,qty)
      values (v_line->>'ingredient_id', p_to, (v_line->>'qty')::numeric)
      on conflict (ingredient_id,location_id)
      do update set qty = stock_levels.qty + (v_line->>'qty')::numeric,
                    updated_at = now();
    end if;

    insert into stock_moves(doc_id,type,ingredient_id,qty,from_location,to_location,unit_cost,actor)
    values (v_doc,p_type,v_line->>'ingredient_id',(v_line->>'qty')::numeric,
            p_from,p_to,(v_line->>'unit_cost')::numeric,p_actor);

    v_total := v_total + (v_line->>'qty')::numeric
                       * coalesce((v_line->>'unit_cost')::numeric,0);
  end loop;

  update stock_docs set total_cost = v_total where id = v_doc;
  return v_doc;
end $$;
```

**ผลพลอยได้:** การขายก็เรียก RPC นี้ (`type='sale_out'`, `from='front'`) → **ปัญหา race condition หายไปทั้งหมด**

## 3. หน้าจอที่จะเพิ่มในหลังบ้าน

### 3.1 เมนูใหม่ในแถบซ้าย

```
จัดการสต็อก
├─ ภาพรวมสต็อก        ← ตารางไขว้: วัตถุดิบ × สถานที่
├─ รับของเข้าคลัง      ← กรอกหลายรายการพร้อมกัน (ซื้อของ)
├─ เบิกมาหน้าร้าน      ← คลัง → หน้าร้าน
├─ จ่ายออกสาขา        ← คลัง → สาขาที่ยังไม่มี POS
├─ ปรับยอด / ของเสีย   ← นับจริงแล้วปรับ, ของหมดอายุ
└─ ประวัติเคลื่อนไหว    ← ledger ทั้งหมด กรองได้
```

### 3.2 หน้า "ภาพรวมสต็อก"

```
วัตถุดิบ          หน่วย    คลังหลังร้าน   หน้าร้าน    รวม      สถานะ
─────────────────────────────────────────────────────────────────
นมสด             ml       12,000       4,200     16,200   ✅
เมล็ดกาแฟ         g         5,000         850      5,850   ⚠️ หน้าร้านใกล้หมด
แก้ว 16 oz        ใบ          500          80        580   ⚠️ หน้าร้านใกล้หมด
หลอด             ชิ้น          0         120        120   🔴 คลังหมด
```
คลิกแถวไหน → เห็นประวัติเคลื่อนไหวของตัวนั้น

### 3.3 หน้า "รับของเข้าคลัง" (เพิ่มทีละหลายรายการ)

```
┌────────────────────────────────────────────────────────┐
│ ผู้ขาย [แม็คโคร        ]  วันที่ [29/08/2026]           │
│ เลขที่บิล [INV-8842   ]  หมายเหตุ [                 ]   │
├────────────────────────────────────────────────────────┤
│ วัตถุดิบ        จำนวน   หน่วย    ต้นทุน/หน่วย   รวม      │
│ [นมสด      ▾]  [ 10 ]  [ลัง ▾]  [   48.00 ]  ฿480  [×]│
│ [เมล็ดกาแฟ  ▾]  [  5 ]  [กก. ▾]  [  620.00 ]  ฿3,100[×]│
│ [แก้ว16oz  ▾]  [  1 ]  [ลัง ▾]  [1,075.00 ]  ฿1,075[×]│
│ [+ เพิ่มรายการ]                                        │
├────────────────────────────────────────────────────────┤
│                                    รวมทั้งสิ้น  ฿4,655  │
│              [ ยกเลิก ]  [ บันทึกรับของเข้าคลัง ]        │
└────────────────────────────────────────────────────────┘
```

**จุดสำคัญ — หน่วยซื้อ vs หน่วยใช้:** เลือก "ลัง" ระบบแปลงเป็น ml ให้อัตโนมัติ (1 ลัง = 12,000 ml) และคำนวณต้นทุนต่อ ml ใหม่ให้เอง — ไม่ต้องคูณเลขเอง

### 3.4 หน้า "เบิกมาหน้าร้าน" / "จ่ายออกสาขา"

หน้าตาเหมือนกัน ต่างที่ปลายทาง:

```
จาก [คลังหลังร้าน ▾]  ไป [หน้าร้าน ▾ / สาขาบางจาก ▾]
ผู้เบิก [ชื่ออัตโนมัติ]

วัตถุดิบ        คลังมี      จำนวนที่เบิก   หน่วย
[นมสด      ▾]  12,000 ml  [  6,000  ]  ml   [×]
[หลอด      ▾]       0 ชิ้น  [    200  ]  ชิ้น  [×]  ⚠️ คลังไม่พอ
```
- แสดงยอดคงเหลือของต้นทางแบบสด
- **เตือนถ้าเบิกเกินที่มี** (แต่ยอมให้บันทึกได้ถ้ายืนยัน — ของจริงอาจนับไม่ตรง)
- ปุ่มลัด "เบิกตามที่ขาดหน้าร้าน" — คำนวณให้เองว่าควรเบิกอะไรเท่าไร

### 3.5 หน้าขาย (POS) — เปลี่ยนแค่จุดเดียว

ตัดสต็อกจาก `front` แทนที่จะตัดจากตัวเลขรวม + เรียกผ่าน RPC
หน้าตาผู้ใช้ **ไม่เปลี่ยนเลย**

## 4. งานทั้งหมดที่จะทำ (ถ้าอนุมัติ)

| กลุ่ม | งาน | ผลกระทบต่อไฟล์ |
|---|---|---|
| **A. Security (Sprint 0)** | Supabase Auth, lockdown RLS, hash PIN, DB constraints, `created_at` จาก DB, เก็บบิลที่ส่งไม่สำเร็จ, CSV injection fix | ทั้ง 2 ไฟล์ + SQL ใหม่ |
| **B. คลังสินค้า (ใหม่)** | ตาราง+RPC ตามข้อ 2, หน้าจอ 6 หน้าตามข้อ 3, แปลงหน่วยซื้อ | `admin.html` เพิ่ม ~900 บรรทัด |
| **C. Data Integrity** | แยก `app_config` → ตารางจริง, ขายผ่าน RPC, เลิก state ใน DOM | ทั้ง 2 ไฟล์ |
| **D. Performance** | DB view สำหรับรายงาน, debounce ค้นหา, pagination | ทั้ง 2 ไฟล์ |
| **E. Code Quality** | แยก `/shared/core.js` + `domain.js`, ถอดหลังบ้านออกจาก POS, design token, friendly error | โครงไฟล์เปลี่ยน |
| **F. UX** | 86 เมนูจากหน้าขาย, accessibility, host QR lib เอง | ทั้ง 2 ไฟล์ |

**ประเมินเวลา:** 3–4 สัปดาห์ถ้าทำครบ · แนะนำแบ่งเป็น 3 รอบส่งงาน

## 5. ❓ คำถามที่ต้องเคาะก่อนเริ่ม

### 🔴 ข้อ 1 — วิธี deploy ปัจจุบัน (สำคัญที่สุด ตอบก่อนข้ออื่น)

ตอนนี้คุณเอาไฟล์ขึ้น Cloudflare Workers ยังไง?
- **(ก)** ก็อปโค้ดวางใน dashboard ทีละไฟล์
- **(ข)** ใช้ `wrangler deploy` จากเครื่อง
- **(ค)** เชื่อม GitHub ให้ deploy อัตโนมัติ

**ทำไมสำคัญ:** ถ้าเป็น (ก) การแยกไฟล์เป็น `/shared/core.js` จะทำให้ deploy ยุ่งยากขึ้นมาก → ผมจะเลือกวิธีอื่นแทน (เช่น รวมไฟล์ตอน build หรือคงไฟล์เดียวแต่จัดระเบียบข้างใน)

### 🔴 ข้อ 2 — สถานที่มีอะไรบ้าง ชื่อจริงว่าอะไร

จากภาพ FoodStory เห็น 2 สาขา: **โรงพยาบาลพนม...** และ **ปั๊มบางจาก 304**

ขอให้ระบุ:
- คลังหลังร้าน อยู่ที่สาขาไหน / เรียกว่าอะไร
- สาขาที่ **มี POS** (ที่กำลังทำอยู่นี้) คือสาขาไหน
- สาขาที่ **ยังไม่มี POS** (รับของจากคลัง) มีกี่แห่ง ชื่ออะไร

### 🟠 ข้อ 3 — หน่วยซื้อ vs หน่วยใช้ เอาไหม

เช่น ซื้อนมเป็น **ลัง** (1 ลัง = 12 กล่อง × 1,000 ml) แต่สูตรใช้เป็น **ml**

- **(ก)** เอา — ระบบแปลงให้ ตอนรับของเลือกหน่วยซื้อได้ *(แนะนำ — ลดการคำนวณผิด)*
- **(ข)** ไม่เอา — กรอกเป็นหน่วยเล็กเสมอ (ง่ายกว่า แต่ต้องคูณเอง)

ถ้าเลือก (ก) รบกวนส่งตัวอย่างมา 3–5 รายการ เช่น "นม: ซื้อเป็นลัง 1 ลัง = 12,000 ml ราคาลังละ 480"

### 🟠 ข้อ 4 — ของที่ขายหน้าร้านโดยตรง (ขนม/น้ำอัดลม) นับสต็อกยังไง

พวก กล้วยตาก / ทองม้วน / น้ำอัดลม / ทิชชู่ — ไม่มีสูตร แต่เป็นของที่ต้องเบิกจากคลัง

- **(ก)** ทำเป็น "วัตถุดิบ" ที่ผูกสูตร 1:1 กับเมนู (ขาย 1 ถุง = ตัด 1 ถุง) *(แนะนำ — ระบบเดียวกันหมด)*
- **(ข)** แยกเป็นสินค้าสำเร็จรูปอีกประเภท

### 🟡 ข้อ 5 — ใครมีสิทธิ์ทำอะไร

| งาน | ใครทำได้ (เสนอ) |
|---|---|
| ขายหน้าร้าน | พนักงาน + แอดมิน |
| เบิกคลัง → หน้าร้าน | พนักงาน + แอดมิน |
| รับของเข้าคลัง | **แอดมินเท่านั้น** |
| จ่ายออกสาขา | **แอดมินเท่านั้น** |
| ปรับยอด / ของเสีย | **แอดมินเท่านั้น** |
| ดูรายงาน/ต้นทุน | **แอดมินเท่านั้น** |

โอเคตามนี้ไหม หรืออยากให้พนักงานทำได้มากกว่านี้/น้อยกว่านี้

### 🟡 ข้อ 6 — ข้อมูลเดิมที่มีอยู่

สต็อกวัตถุดิบที่ใส่ไว้ตอนนี้ (9 รายการตัวอย่าง) จะให้:
- **(ก)** ย้ายทั้งหมดไปเป็นของ "หน้าร้าน"
- **(ข)** ย้ายทั้งหมดไปเป็นของ "คลัง"
- **(ค)** ล้างทิ้ง เริ่มนับใหม่ *(แนะนำ เพราะเป็นข้อมูลตัวอย่าง)*

### 🟡 ข้อ 7 — ลำดับการส่งงาน

- **(ก)** ทำ Security ก่อน (1 สัปดาห์) → ส่ง → แล้วค่อยทำคลัง *(แนะนำ — ปิดช่องโหว่ก่อน)*
- **(ข)** ทำคลังก่อน (2 สัปดาห์) → ส่ง → แล้วค่อย Security
- **(ค)** ทำทั้งหมดแล้วส่งทีเดียว (3–4 สัปดาห์)

## 6. สรุปสิ่งที่ผมแนะนำ (ถ้าไม่อยากตอบทีละข้อ)

ตอบว่า **"ตามที่แนะนำ"** = ผมจะทำตามนี้:

| ข้อ | เลือก |
|---|---|
| 1 | ต้องรู้คำตอบ — **ตอบข้อนี้ข้อเดียวก็เริ่มได้** |
| 2 | ต้องรู้ชื่อสาขาจริง |
| 3 | (ก) เอาหน่วยซื้อ — ตั้ง factor เองได้ทีหลัง |
| 4 | (ก) ทำเป็นวัตถุดิบผูกสูตร 1:1 |
| 5 | ตามตารางที่เสนอ |
| 6 | (ค) ล้างข้อมูลตัวอย่าง เริ่มนับใหม่ |
| 7 | (ก) Security ก่อน แล้วค่อยคลัง |

**ขั้นต่ำที่ต้องตอบเพื่อเริ่มงาน: ข้อ 1 และ ข้อ 2**
